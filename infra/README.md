# CareerGap AI infrastructure

AWS CDK (TypeScript) for running CareerGap AI on **ECS Fargate**, deployed by GitHub Actions
([`.github/workflows/main.yml`](../.github/workflows/main.yml)).

```
                       Internet
                          |
              ALB (HTTPS, certificate from ACM)
              /api/*  |      everything else
                 API service        Web service        (Fargate, private subnets)
              (NestJS, :3001)       (Next.js, :3000)
              |      |      |
        RDS PostgreSQL   ElastiCache Redis   S3 uploads        (isolated subnets / private bucket)
        (pgvector)       (Bull job queues)
```

One host name serves both apps (`/api/*` goes to the API), so the browser sees a single origin and the login cookies work.

## What it creates

| Area | Resources |
|---|---|
| Network | VPC across 2 zones: public (load balancer), private (tasks, outbound through NAT) and isolated (data) subnets; S3 gateway endpoint |
| Data | RDS PostgreSQL 16 (encrypted, backups, Multi-AZ and deletion protection when `production=true`), ElastiCache Redis 7 (`noeviction`, as the job queue requires), private S3 bucket for resumes |
| Compute | ECS cluster, API service (1 vCPU, 2 GB) and web service (0.5 vCPU, 1 GB), deployment circuit breaker with automatic rollback |
| Edge | Application Load Balancer with HTTP redirected to HTTPS |
| Registry | ECR repositories `careergap/api` and `careergap/web` (scan on push, 30 newest images kept) |
| Secrets | `careergap/jwt-secret` and `careergap/jwt-refresh-secret` (generated), `careergap/providers` (you fill in), database credentials (generated by RDS) |
| CI/CD | GitHub OIDC provider and role `careergap-github-deploy` (no stored AWS keys); SSM parameter `/careergap/image-tag` holding the deployed version |

Secrets are injected into the containers by ECS at start-up; none are in the template, the images or GitHub.

## Prerequisites

- An AWS account and credentials that can create these resources (for the first deploy only).
- The CDK bootstrapped once per account and region: `npx cdk bootstrap aws://ACCOUNT/REGION`.
- A **domain name** and an **ACM certificate** for it, in the same region as the stack (DNS validated).
  HTTPS is required: login cookies are marked `Secure`, so the app cannot sign anyone in over plain HTTP.
- Node 20 or newer locally. Docker is not needed; the images are built by GitHub Actions.

## First deployment

1. **Create the infrastructure** with no running tasks (no image exists yet):

   ```bash
   cd infra
   npm ci
   npx cdk diff   -c publicUrl=https://app.example.com -c certificateArn=arn:aws:acm:REGION:ACCOUNT:certificate/ID
   npx cdk deploy -c publicUrl=https://app.example.com -c certificateArn=arn:aws:acm:REGION:ACCOUNT:certificate/ID -c initialDeploy=true
   ```

   Add `-c production=false` for a cheaper test environment (single NAT gateway, small single-node database and cache).
   If the account already has a GitHub OIDC provider (it can only have one), add `-c githubOidcProviderArn=arn:aws:iam::ACCOUNT:oidc-provider/token.actions.githubusercontent.com`.

2. **Point your domain at the load balancer.** Create a CNAME (or a Route 53 alias) from the host in `publicUrl` to the `AlbDnsName` output.

3. **Fill in the secret** `careergap/providers` (output `ProviderSecretName`) in the AWS console, under *Secrets Manager > Retrieve value > Edit*.
   Keys: `NVIDIA_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`.
   Leave a key empty to switch that feature off: without an AI key the AI features report that no provider is configured, and without OAuth keys only that provider's login is unavailable.
   Keep the `unused` key; it is harmless. Values are read when a task starts, so restart the services after changing them
   (`aws ecs update-service --cluster careergap --service careergap-api --force-new-deployment`).

4. **Configure GitHub** (repository *Settings*):
   - *Environments > New environment* named **`production`**. Add *required reviewers* so a person approves each deploy. The AWS role only trusts jobs running in this environment.
   - *Secrets and variables > Actions > Variables*:

     | Variable | Value |
     |---|---|
     | `AWS_REGION` | The stack's region, e.g. `us-east-1` |
     | `AWS_DEPLOY_ROLE_ARN` | Stack output `DeployRoleArn` |
     | `PUBLIC_URL` | The same `publicUrl`, e.g. `https://app.example.com` (baked into the web bundle at build time) |
     | `API_DESIRED_COUNT`, `WEB_DESIRED_COUNT` | Optional; tasks to start on the first deploy (default 1) |

   No AWS keys are stored in GitHub.

5. **Deploy.** Merge to `main` (or run the workflow manually), then approve the `production` environment. The pipeline checks, builds and pushes both images,
   runs the database migrations as a one-off task (this creates the `vector` extension), then rolls out the services and waits for them to be healthy.

## Everyday use

- **Application deploys** happen on every push to `main` that passes the checks. Nothing else is needed.
- **Infrastructure changes**: edit the stack, then `cdk diff` and `cdk deploy` with the same `-c` values as before, **without** `initialDeploy`.
  The running version is kept because task definitions read the tag from `/careergap/image-tag`.
- **Rollback**: a failing rollout is rolled back automatically and the workflow fails. To go back to an earlier version later, re-run the workflow for that commit
  (migrations are not undone, so write them to be backward compatible: add before you remove).
- **Logs**: CloudWatch log groups of the API and web services (names in the stack's resources). Container Insights is on for the cluster.
- **Health**: `GET /api/v1/health` (process is up) and `GET /api/v1/health/ready` (database reachable).

## Good to know

- **Database passwords** are generated by RDS and never leave Secrets Manager. The API container assembles `DATABASE_URL` at start-up from the separate values
  (see `apps/api/docker-entrypoint.sh`), so no composite secret has to be stored.
- **Redis traffic is not encrypted in transit.** The queue client does not use TLS; Redis sits in isolated subnets and accepts connections only from the API tasks.
- **Cost drivers**: NAT gateways, the load balancer, RDS, ElastiCache and Fargate tasks. `production=false` and `natGateways=1` reduce them for testing.
- **The API image is large** because it keeps the build tooling and the Prisma CLI (needed to run migrations in the same image). Slimming it is a possible follow-up.
- **Not included**: autoscaling, WAF, alarms and dashboards, a staging environment, and DNS records. They can be added to the stack.
- **Deleting**: the stack has termination protection. With `production=true` the database, bucket, repositories and logs are retained when the stack is destroyed.
